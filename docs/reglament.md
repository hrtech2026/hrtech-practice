# Регламент практики

## 1. Что сдаётся

Четыре обязательных документа в репозитории команды. Каждый закрывает один этап.

| Документ | Этап | Содержание |
|---|---|---|
| `docs/01_problem.md` | Проблематизация | противоречие, бизнес-цель, метрики, границы решения |
| `docs/02_asis_analysis.md` | AS-IS | модель процесса, источники, найденные проблемы, оценка потерь |
| `docs/03_tobe_architecture.md` | TO-BE и HITL | целевой процесс, архитектура, контур человека, риски ИИ |
| `docs/04_requirements.md` | Требования | User Stories, Use Cases, нефункциональные требования |

## 2. Как сдаётся

1. Работа идёт через Pull Request в ветку `main`.
2. В каждом Pull Request проверяется `validate-docs.yml`. Красная проверка
   означает, что этап не принят.
3. Коммит называется с указанием этапа: `docs(asis): …`, `feat(tobe): …`.
4. Сдача этапа — комментарий в Pull Request: `Сдаю этап 2 (AS-IS)`.
5. Колонку этапа на доске ставит пульт по содержимому репозитория: сданный
   документ переносит команду в следующую колонку в течение суток-двух.
   Переводить карточку вручную не нужно — прав на запись на доске нет.
6. Если Pull Request устарел — его уже влили другим запросом или он потерял
   смысл — закройте его сами и напишите в комментарии причину. Висящий запрос
   не считается сданным этапом и мешает читать историю.

Что проверяет автоматика:

| Проверка | Что будет, если не выполнена |
|---|---|
| Наличие обязательных файлов | ошибка `file.missing` |
| Ключи YAML-фронтматтера | ошибка `frontmatter.key` |
| Обязательные секции документа | ошибка `section.missing` |
| Диаграмма в AS-IS и TO-BE | ошибка `diagram.missing` |
| Секция `## Human-in-the-Loop` | ошибка `section.missing` |
| Непустая секция HITL | ошибка `section.empty` |
| Незаполненные заготовки | ошибка `placeholder.*` |
| Состав команды 3–5 человек | ошибка `meta.team_size` |
| Обязательные роли в составе | ошибка `meta.required_role` |

Автоматика ловит формальные пропуски. Содержательные ошибки — это работа
рецензирования и защиты.

## 3. Роли в команде

| Роль | Отвечает за |
|---|---|
| Капитан | репозиторий, этапы, сдачу работы |
| Аналитик процессов | `01_problem.md`, `02_asis_analysis.md` |
| Архитектор решения | `03_tobe_architecture.md` |
| Требования и качество | `04_requirements.md`, ревью чужих документов |
| Исследователь данных | метрики, источники, оценка эффекта |

Обязательны капитан, аналитик и архитектор. Один человек не совмещает больше
двух ролей. Команда — от 3 до 5 человек.

Капитан ведёт репозиторий и сдачу, но **не может быть единственным автором
артефактов**: репозиторий, где все коммиты одного человека, не проходит
критерий 4 «Работа с репозиторием» в [`criteria.md`](criteria.md).

## 4. Работа с репозиторием

- ветка `main` защищена, все изменения через Pull Request;
- в одном Pull Request — один этап, кроме исправлений по замечаниям;
- состав команды в `data/meta.yml` заполнен: логины и роли проставляет
  преподаватель по заявке, сам файл правьте только через заявку;
- поле `stage` в `data/meta.yml` справочное: его выставляет пульт по
  содержимому репозитория, команда его не правит. Колонка на доске и
  «Фактический_этап» считаются по артефактам, а не по этому полю;
- `README.md` команды заполнен: название, трек, состав с именами, концепт.
  Колонка «Участник» в таблице состава попадает на витрину проектов вместе
  с ролями, логины остаются приватными.

## 5. Внутреннее ревью и слияние

Рецензирование между командами — отдельный этап, он описан в §7. Здесь —
ревью внутри команды, без которого этап не считается сданным.

| Этап | Ведёт | Обязательно читает до слияния |
|---|---|---|
| Проблематизация | Аналитик | Капитан, архитектор |
| AS-IS | Аналитик | Архитектор, требования |
| TO-BE и Human-in-the-Loop | Архитектор | Аналитик, капитан |
| Требования | Требования | Все остальные |

Что считается ревью: **Approve** в Pull Request либо комментарий с решением
по каждому замечанию. Молчаливое «посмотрел» ревью не считается.

Слияние делает автор Pull Request, когда проверка `validate-docs.yml` зелёная
и ревью получено. Ждать преподавателя не нужно: он не обязательный ревьюер и
не единственный, кто может слить запрос. Красная проверка — запрос не
сливается, сначала исправления.

## 6. Защита

| Параметр | Значение |
|---|---|
| Формат | 10–12 минут презентации + 5–8 минут вопросов |
| Демонстрация | обязательна: прототип, сценарий с карточками или разбор рискованного шага |
| Состав | вся команда, каждый говорит хотя бы раз |
| Материалы | презентация в репозитории команды, артефакты уже в `main` |

Пять вопросов, которые задаются на защите, и требования к ответам — в
[`methodology.md`](methodology.md). Оценка и порядок апелляции — в
[`criteria.md`](criteria.md). Дата — в [`timeline.md`](timeline.md).

## 7. Взаимное рецензирование

На предпоследней неделе каждая команда получает рецензию от двух других
команд. Назначения публикуются в этом репозитории, следите за Issue с меткой
`needs-triage` и за [`docs/timeline.md`](timeline.md).

Отчёт приходит в обезличенном виде: расклад по критериям и сгруппированные
замечания, без имён рецензентов. Замечания нужно либо учесть, либо обосновать
отказ от них на защите.

Оценка рецензента **не** влияет на вашу итоговую оценку.

Канал оформления рецензии преподаватель объявит отдельно. Ожидайте Issue в этом
репозитории — не начинайте сами: несогласованные заявки не засчитываются.

## 8. Дедлайны и просрочка

- Дедлайн — 23:59 по часовому поясу вуза, даты в [`timeline.md`](timeline.md).
- Просрочка: −10% за каждый полный день, после третьего дня работа не принимается.
- Проблемы с техникой и сетью не являются основанием для переноса.

## 9. Вымышленные данные

Если данные иллюстративные, а не реальные, пометьте их явно:

```text
> ⚠ Данные иллюстративные, основаны на допущении о среднем размере команды
> в 120 человек. Источник — отраслевые бенчмарки.
```

Отсутствие пометки при обнаружении расхождения с заявленным источником снимает
до 10 баллов. Выдуманные данные без пометки — до 20 баллов.

## 10. Использование чужой работы

Цитируйте и указывайте источник. Использование работ прошлых лет,
готовых решений и генерации вместо собственного анализа — работа
не оценивается, −30 баллов к итогу.
