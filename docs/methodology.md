# Методические указания

Четыре документа, четыре этапа. Ниже — что должно быть в каждом и как это
проверяется. Подробные версии документов лежат в вашем командном репозитории
как комментарии в самих файлах-шаблонах.

Автоматическая проверка ловит формальные пропуски: наличие файла, ключи
фронтматтера, обязательные разделы, незаполненные заготовки (см.
[`getting_started.md`](getting_started.md) и [`faq.md`](faq.md)). Ниже, в конце
каждого этапа, — **содержательные критерии приёмки**: по ним этап принимается
или возвращается на доработку. Проверьте себя по списку до того, как откроете
Pull Request.

## Этап 1. Противоречие

**Главная ошибка — начать с решения.** «Внедрить AI-чат-бота» — это гипотеза,
а не проблема. Проблема формулируется наблюдаемо:

```text
В контексте <процесс>
при <событие>
происходит <наблюдаемое последствие>
из-за чего <причина>
в результате <ущерб и для кого> (<источник>)
```

Что обязательно есть: роль-носитель проблемы, заинтересованные стороны,
измеримая бизнес-цель с ограничением, 2–4 метрики с текущим значением,
границы решения и допущения.

Подробности: комментарии в `docs/01_problem.md` вашего репозитория.

**Этап сдан, если:**

- [ ] противоречие сформулировано по схеме: контекст → событие → последствие → причина → ущерб;
- [ ] названа роль-носитель проблемы;
- [ ] указаны заинтересованные стороны, не менее одной;
- [ ] бизнес-цель измерима и есть ограничение, не дающее ухудшить качество;
- [ ] 2–4 метрики с текущим значением и источником;
- [ ] есть раздел «Границы решения» с явными исключениями;
- [ ] допущения отделены от фактов.

## Этап 2. AS-IS

Процесс моделируется, а не описывается словами. Обязательна Mermaid-диаграмма
с подграфами по ролям — иначе невозможно увидеть, где заканчивается зона
ответственности человека.

| Что | Зачем |
|---|---|
| Границы процесса: начало, конец, что вне процесса | обозримость, 7–15 шагов |
| Таблица шагов: роль, вход, выход, система, время, частота | основание для расчёта потерь |
| Источник у каждого утверждения | отделяет факт от мнения |
| Классификация найденных проблем | лишний шаг, ожидание, дублирование, невидимое знание, точка отказа, потеря мотивации |
| Оценка потерь хотя бы по одной метрике | делает обоснование проверяемым |

Отметьте места, где сотрудник обходит процесс. Обходной путь — самый сильный
аргумент в пользу автоматизации: значит, проблема признана участниками.

Подробности: `docs/02_asis_analysis.md` вашего репозитория.

**Этап сдан, если:**

- [ ] названы границы процесса: начало, конец, что вне процесса;
- [ ] есть Mermaid-диаграмма с подграфами по ролям;
- [ ] все шаги диаграммы описаны таблицей: роль, вход, выход, система, время, частота;
- [ ] каждое утверждение о фактах имеет источник;
- [ ] найденные проблемы классифицированы, у каждой оценено влияние;
- [ ] посчитаны потери хотя бы по одной метрике времени.

## Этап 3. TO-BE и Human-in-the-Loop

Самый оцениваемый этап: 60 балсов из 100.

### Уровни автоматизации

| Уровень | Что делает система |
|---|---|
| L0 | человек делает всё, система хранит |
| L1 | система готовит сводку, человек решает |
| L2 | система предлагает с обоснованием, человек подтверждает |
| L3 | система действует сама ниже порога риска, выше — эскалация |
| L4 | система действует без участия человека |

Правило: **чем выше цена ошибки, тем ниже уровень**. Уровень выбирается
не по возможностям модели, а по цене ошибки и обратимости решения.
Увольнение, отказ в найме, отказ в повышении — не выше L1.

### Точки вмешательства

Каждая точка — строка таблицы с условием срабатывания, правом на отказа,
сроком и эскалацией. Точка без условия — не точка, а декларация.

### Объяснимость

Нужен реальный пример вывода системы: какие признаки повлияли, какие данные
использовались, почему результат такой, что должен проверить человек.
Фраза «модель объяснима» без примера баллов не даёт.

### Риски ИИ

Пройдите чек-лист рисков и выпишите применимые: справедливость, прозрачность,
данные, надёжность, влияние на людей, право, качество данных, безопасность.
Для каждого: сценарий, контрмера, способ проверки. Отдельно перечислите
риски, которые вы **приняли сознательно**.

Подробности: `docs/03_tobe_architecture.md` вашего репозитория.

**Этап сдан, если:**

- [ ] каждая проблема AS-IS имеет явный ответ в целевом процессе;
- [ ] рассмотрены и отклонены альтернативы, выбор обоснован;
- [ ] секция `## Human-in-the-Loop` не пуста;
- [ ] таблица точек вмешательства: условие, право на отказ, эскалация, срок;
- [ ] для необратимых решений уровень автоматизации не выше L1;
- [ ] приведён реальный пример объяснения решения системой;
- [ ] таблица рисков ИИ: сценарий, контрмера, способ проверки;
- [ ] указан контур данных и что уходит за пределы организации;
- [ ] определён состав журнала решений.

## Этап 4. Требования

Требование записано, если у него есть критерии приёмки. Story без критериев —
намерение, а не требование.

```text
Как <роль>, я хочу <действие>, чтобы <выгода>.

Given <состояние>, When <действие>, Then <наблюдаемый результат>
```

Нефункциональные требования обязательны: безопасность, приватность, аудит,
объяснимость, производительность, надёжность.

Нефункциональные требования, которые чаще всего забывают и которые проверяют
на защите: что происходит при недоступности зависимости, какие сроки хранения
данных, кто имеет доступ к журналу решений.

В конце — таблица трассируемости: каждое требование связано с источником
в TO-BE и с проблемой из AS-IS.

Подробности: `docs/04_requirements.md` вашего репозитория.

**Этап сдан, если:**

- [ ] User Stories в формате «как <роль>, я хочу …, чтобы …»;
- [ ] у каждой Story есть критерии приёмки в Given/When/Then;
- [ ] минимум два Use Case с альтернативными сценариями и исключениями;
- [ ] нефункциональные требования: безопасность, приватность, аудит, объяснимость;
- [ ] есть ограничения и допущения, разделённые между собой;
- [ ] трассируемость: требования связаны с TO-BE и рисками.

## Пять вопросов, которые зададут на защите

1. Какое решение в вашем контуре необратимо для человека?
2. Где человек может сказать «нет» и как это технически реализовано?
3. Что будет, если модель ошибётся на массовой выборке?
4. Как сотрудник узнает, что решение приняла машина?
5. Сколько времени человек тратит на систему — больше или меньше, чем до
   автоматизации?

Подготовьте ответы заранее. Команда без ответа хотя бы на один вопрос
получает замечание в критерий 3.

## Диаграммы

Диаграммы пишутся на Mermaid и рендерятся прямо в репозитории. Один блок —
один процесс, подграфы соответствуют ролям, точки вмешательства помечены
`H1`, `H2` и сведены в таблицу.

Требования к диаграмме:

- обязательна в `02_asis_analysis.md` и `03_tobe_architecture.md`;
- все узлы диаграммы описаны в таблице шагов, и наоборот;
- неотрендеренный блок означает синтаксическую ошибку — она ломает ревью;
- один процесс на один блок, «лесов» из стрелок быть не должно.
