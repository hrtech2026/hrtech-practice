# Как начать работу

Пошаговая инструкция от нуля до первого принятого этапа. Пройдите по пунктам
по порядку — каждый следующий зависит от предыдущего.

## Что нужно до заявки

- **Аккаунт GitHub.** Логины из заявки станут вашими логинами в репозитории
  команды. Один аккаунт на человека. Больше ничего не нужно: вступать в
  организацию **не требуется**, никто не приглашает вас вручную.
- **От 3 до 5 логинов** и решение, кто капитан. Капитан отвечает за репозиторий
  и за сдачу этапов.

## Шаг 1. Подайте заявку

**New issue → Заявка на команду** в этом репозитории.

| Поле | Что важно |
|---|---|
| Название команды | То, что увидит витрина проектов |
| Трек | Предметная область: найм, онбординг, выгорание, оценка, обучение, прочее |
| Номер группы | Например `ИП-215`, используется в расписании защит |
| Номер команды в группе | Двузначное число, определяет имя репозитория `team-<трек>-<NN>` |
| Участники (GitHub) | От 3 до 5 логинов через запятую |
| Капитан | Один из логинов выше |
| Одно предложение о концепте | До 200 символов, попадёт на витрину |

Три галочки в разделе «Подтверждение» — не формальность. Каждая проверяется,
и заявка без них не пройдёт.

Логины проверяются автоматически: аккаунт должен существовать, а человек не
должен состоять в другой команде. Если логин написан с ошибкой, в заявку
придёт комментарий со списком проблем — исправьте поле и напишите
преподавателю.

Преподаватель делает ровно одно действие — добавляет метку `provision`.
Выдачу прав, создание репозитория и приглашения он не делает руками.

## Шаг 2. Дождитесь допуска

Дальше происходит так:

1. Автоматика подтверждает приём заявки комментарием.
2. Преподаватель сверяет состав с журналом группы.
3. Преподаватель добавляет метку `provision` — и репозиторий создаётся.

**Пока метки нет, ничего не создаётся.** Это занимает время, спешить не нужно.

На этом этапе заявку ещё можно править. Преподаватель может заметить, что
состав указан неверно, и попросить исправить: отредактируйте нужные поля
прямо в том же Issue, правки подхватятся автоматически.

**После допуска заявку править нельзя.** Изменение состава — отдельная
заявка, см. [«Если состав изменился»](#если-состав-изменился).

## Шаг 3. Примите приглашение и получите репозиторий

В заявку придёт комментарий: ссылка на репозиторий и таблица прав.

```text
| Участник  | Права    |
|-----------|----------|
| @ivanov   | капитан  |
| @petrova  | участник |
```

- Капитан может управлять репозиторием, участники — писать в код.
- **Приглашать никого не нужно.** Права выдаются автоматически по заявке.

### Шаг 3.1. Нажмите Accept в письме

**Это единственное ручное действие во всём процессе, и оно ваше, не
преподавателя.** GitHub отправляет каждому участнику из заявки письмо с
приглашением в репозиторий. Пока приглашение не принято, участник не может
ничего записать — неважно, создана уже папка или нет.

1. Откройте письмо от GitHub на `@github.com`.
2. Нажмите **Accept**.
3. Проверьте, что репозиторий открывается и в нём виден ваш логин.

Письмо может прийти не сразу. Не нашли — подождите пару минут и проверьте спам.
Приглашение не протухает, принять можно в любой момент.

> **Про членство в организации.** Оно не требуется. Приглашение в репозиторий
> GitHub присылает всем одинаково, независимо от того, состоит человек в
> организации или нет. Преподаватель не приглашает никого вручную.

В репозитории лежит эталон: `docs/` с заготовками и `README.md` с
подсказками. Это нормально, их нужно заменить.

`data/meta.yml` заполнен автоматически по вашей заявке: логины, роли, трек,
группа, номер, название, концепт и дата. **Не трогайте `members`** — составом
ведёт преподаватель, и ваши правки будут перезаписаны.

## Шаг 4. Первый Pull Request

```bash
git clone https://github.com/<орг>/team-<трек>-<NN>.git
cd team-<трек>-<NN>
git switch -c feat/problem
```

Замените содержимое:

- `README.md` — название, трек, состав, концепт. Требования к содержимому
  написаны комментарием в самом файле. В таблице состава заполните колонку
  «Участник»: эти имена вместе с ролями показывает витрина проектов, а
  логины остаются приватными.
- `docs/01_problem.md` — первый документ.
- `data/meta.yml` — **имена** участников (в записи пустые), `stakeholders` и
  `concept`. Имена нужны, чтобы команда появилась в составе на витрине.

```bash
git add -A
git commit -m "docs(problem): описать противоречие и границы решения"
git push -u origin feat/problem
```

Откройте Pull Request в GitHub. Проверка **«Проверка документов»** запустится
сама. Ветка `main` защищена, поэтому без зелёной проверки Pull Request не
слить.

### Что именно проверяется

Проверка смотрит на **состав изменений**, а не на дерево целиком:

- если запрос меняет `docs/`, `README.md` или сам валидатор — проверяется форма
  всех документов, а содержание — только тех, что команда уже начала (см.
  «Какие документы проверяются» ниже);
- если изменён только `data/` — а так меняют состав, когда кто-то
  присоединяется, уходит или становится капитаном, — проверяются только
  метаданные команды;
- если не изменилось ничего из перечисленного — например, запрос добавляет
  `.gitignore` или правит оформление CI — не проверяется ничего. Правило
  перечисляет пути, а не файлы, поэтому `.github/` и `CODEOWNERS` относятся
  к последнему случаю.

Причина в том, что состав меняется автоматически, а команда к этому моменту
могла ещё не написать ни одного документа. Если бы проверка всегда требовала
заполненные документы, первая же смена капитана упиралась бы в собственные
заготовки `{{ … }}`. Свои правки документов вы по-прежнему сдаёте через
полную проверку, и подставные документы в `main` не попадут.

Круг отвечает на вопрос «стоит ли вообще что-то проверять». А вот заполнен ли
документ, который вы сдаёте, — вопрос отдельный.

**Сразу после создания репозитория проверка зелёная, и так должно быть.** В
`main` лежит эталон с заготовками, их никто не писал и ругаться на них не на
кого. Красная галочка появляется на вашем первом Pull Request и означает
ошибки в ваших правках.

### Какие документы проверяются

По содержанию проверяется документ, который команда **начала**. Начатым он
считается, если в нём не осталось заготовок — то есть вы его уже написали или
почти написали.

| Документ | Что с ним происходит |
|---|---|
| Которого коснулся ваш Pull Request | проверяется целиком: ни `ЗАПОЛНИТЕ`, ни `{{ … }}`, ни `<!-- TODO -->` |
| Который вы уже закончили | проверяется тоже: готовый документ не должен испортиться, пока вы правите другое |
| Все **перед** самым начатым | проверяются: так этапы нельзя перепрыгнуть и сдать `03`, не написав `02` |
| До которого вы ещё не дошли | проверяется только форма: файл на месте и все обязательные разделы на месте |

Форма — это структура, а не содержание: наличие файла, обязательных разделов и
фронтматтера. Её ошибки приходят сразу, как только команда тронула документ,
и заготовками в других документах они не вызваны.

Черновики «ради зелёной галочки» писать не нужно. Если ошибка
`placeholder.*` пришла на документ, которого вы не трогали, — это один из двух
случаев: вы его уже закончили и заготовка в нём вернулась, либо вы начали
более поздний документ, а этот пропустили.

## Шаг 5. Сдайте этап

1. В комментарии к Pull Request напишите: `Сдаю этап 1`.
2. Дальше ничего: колонку этапа на доске ставит пульт по содержимому
   репозитория, и через сутки-двое карточка окажется там, где вы сдали.

## Если проверка красная

Красная проверка — это список конкретных ошибок, а не обвинение. Нажмите на
красную галочку рядом с `Проверка документов` и прочитайте, что не так. Самые
частые:

| Ошибка | Что делать |
|---|---|
| `placeholder.fill_marker` | Осталась строка `ЗАПОЛНИТЕ`. Найдите поиском по файлу |
| `placeholder.mustache` | Осталась подстановка `{{ ... }}` |
| `section.missing` | Нет обязательного раздела. Список — в [`reglament.md`](reglament.md) |
| `diagram.missing` | Нет блока ` ```mermaid `. Нужен хотя бы один непустой |
| `section.empty` | Раздел есть, но пустой. Для Human-in-the-Loop нужны таблица уровней автоматизации, таблица точек вмешательства и пример объяснения |
| `meta.id_mismatch` | В `data/meta.yml` чужой `id`. Напишите преподавателю: файл ведёт он |

Полный список с расшифровкой — [`faq.md`](faq.md).

## Если что-то пошло не так

**В заявке нет комментария, а прошло несколько часов.**
Скорее всего, заявка ждёт допуска преподавателя. Если и через день ответа
нет — напишите через **New issue → Вопрос по практике**, указав номер заявки.

**Заявку отклонили.**
В комментарии перечислены причины. Исправьте поля в том же Issue и напишите
преподавателю — он добавит метку заново, это можно делать сколько угодно раз.

**Репозиторий не создался, а метку уже ставили.**
Посмотрите запуск воркфлота в пульте управления: в комментарии к заявке будет
написано, что именно не сработало. Сообщите преподавателю, приложив номер
заявки.

## Если состав изменился

Ушёл участник, пришёл новый, сменился капитан. Правками в репозитории это не
сделать: права выдаются только по заявке, и `data/meta.yml` перезаписывается
ею же.

**New issue → Изменение состава** — укажите новый состав целиком, а не дельтой
вроде «удалить вот этого». Преподаватель добавит метку `roster`, после чего
права обновятся, а `data/meta.yml` изменится через Pull Request.

Порядок такой: сначала права получают новые участники, потом снимаются со
старых. Если капитан сменился, у прежнего станет роль участника.

## Включите уведомления

Напоминаний от бота не будет: дедлайны живут в GitHub, и напоминает сам
GitHub. Чтобы не пропустить:

- **Watch → Custom → Issues and pull requests** в этом репозитории;
- то же самое в репозитории команды;
- режим **Participating and @mentions** замените на **All activity** — иначе вы
  узнаете о дедлайне, когда он уже прошёл.

Актуальные даты — в [`timeline.md`](timeline.md). Если сдать не готовы, не
молчите: напишите преподавателю через Issue сразу. Молчаливый срыв дедлайна
обсуждения стоит дороже, чем сам сдвиг.
